Ordered vector/scalar MAX/MIN foundation (2026-11-10)
===================================================

The raw control prototype adds vector MAX/MIN (2/3) and scalar MAX/MIN (5/6).
A shared integer-only SPIR-V function compares sign/magnitude and selects the
flushed source bits. Signed zeros compare equal: MAX selects A on a tie, MIN B.
Any unordered comparison selects B. Selected values are not converted through
native floating-point arithmetic, NMin/FMin or a host GLSL compiler. Source
absolute/negate/swizzle and signed-denormal policy follow the existing reference.
NaN payload bits are retained internally, not claimed as hardware-defined.
Scalar operations retain W/X versus W/Z selection for MAD, write scalar history
even with an empty destination and do not change P0. This is vertex-prototype
coverage, not a newly validated Xbox360 hardware specification or complete stage
implementation. Empty loops, resumability, fetches, other ALUs/stages/ROP and
actual correct ready fallback rendering remain unfinished.

The control module is9726 words versus9510 (+216 words/864bytes,~2.3%). The shared
function prevents duplicating its selection code in the vector/scalar cases.
The original program remains6051 words and arithmetic2855. Module identities
are captured per revision; equal word counts do not imply identical bytes.
No cache defaults, driver requirements, draw path or frontend pacing change.

Cold construction now reserves bounded output capacity directly. Actual parent
instrumentation records two allocation requests for control capacity16384words;
current instrumentation records one, with the same final capacity. This avoids
the intermediate8192-word growth request. Physical copied bytes are unmeasured:
realloc may grow in place.1000 exact same-owner warm builds allocate nothing;
first-allocation failure, overflow failure, recovery and balanced release pass.
