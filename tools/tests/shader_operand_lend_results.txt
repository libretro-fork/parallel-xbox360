Change and ownership
--------------------
ALU setup loaded a raw register/float constant separately for every operand,
even when the operands only differed in swizzle or modifiers. Reuse a prior
raw ID within the same scalar/vector ALU setup, matching source kind, the full
32-bit index and addressing mode. Guest data is unchanged between these loads;
LoadOperandStorage emits addressing and loads, not guest writes. Constants are
immutable during the draw. Modifiers/swizzles still execute independently.

The C89 matcher borrows existing operand metadata through a typed field callback.
It scans at most two predecessors, using two12-byte projected keys, no new array,
container, payload buffer, allocation, lock or retained cache. It returns an ID
index into the existing instruction-local operand array. Lookup of operand0,
invalid indices, missing readers and failed projections retains the original
load. The typed bridge only accepts known register/constant sources and the
three known address modes; unsupported inputs still reach original validation.
No reuse crosses instruction boundaries, paired scalar/vector evaluation or
state writes. Dynamic a0/aL addressing must match exactly; it is never treated as
absolute. Fetch operations and resource bindings are untouched.

This removes generated IR loads/access-chain construction and associated
compiler bookkeeping. It does NOT prove fewer actual GPU memory transactions:
the driver may already eliminate those duplicates. No video/audio buffer copies,
GPU uploads or guest-memory ownership are changed. No release logging/readback.
