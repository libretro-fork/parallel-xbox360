C89 direct decoration records, 2026-11-06
Parent: complete 1492903dc2b50e08c3f312bca121091d2ab55f6d sources.

All eleven production decoration factories bypass typed Instruction construction
and std::set<std::unique_ptr<Instruction>> nodes. C89 keys borrow caller words
and text during exact lookup, before allocating anything. Unique records encode
directly into module-owned payload pages; sorted pointer metadata borrows them.
Output borrows the complete encoded record. Target IDs and shader IDs do not
change. The tested x64 Builder shrinks 1456 -> 1408 bytes; Instruction64,
Block136, Function136 and Module88 layouts are unchanged.

Comparison preserves the previous ordering: target ID first, opcode next,
then operand ID/literal flags before unsigned word values, then length. String
words use logical SPIR-V little-endian packing, not lexical text ordering.
Counted linkage text can include NUL and unaligned input. A compact ID interval
represents the contiguous ID-valued operands used by these factories; no
per-word flag bitmap is allocated. Each blob owns an active flag, ID interval
and its raw words (12-byte non-wire prefix). Input is encoded/copied once for
ownership; final module assembly still copies spans into contiguous output.
This is neither zero-copy input ownership nor zero-copy Vulkan submission.

Physical-buffer alignment and alias queries binary-search the target ID and
scan only its records, replacing full set traversal. CFG pruning deactivates
all decorations for an unreachable target. Inactive keys remain cached until
module reset, so re-add reactivates the existing encoding. No typed destructor,
Instruction slots, extra IDs, separate packet allocation or temporary string
encoding buffers are involved. No locks or release logging were introduced.

Cold pointer reserve: 128 entries / 1024 bytes per workspace on x64. Metadata
and payloads grow at checked high-water marks. Input count/pointer/opcode and
65535-word guards precede allocation; metadata or payload allocation failure
preserves prior published records. Sorted insertion can move pointer suffixes;
encoded blobs remain stable. Worst-case insertion metadata work is quadratic
in distinct key count, so descending/permuted construction is measured too.
Pruned names/values are not reclaimed individually within a lease. Payload
allocation can interrupt a previous span's in-place growth. Reset retains
pages/capacity; close frees them. No universal RSS or no-growth claim is made.

Method: Windows x64 GCC16.2 -O2, own-revision C/IR sources and the same benchmark
fixture. C allocator hooks plus C++ new/delete hooks count all relevant user
allocation requests. Requested/tracked memory excludes allocator overhead,
RSS/VRAM and stack objects. Caller vector adapters are built before timing;
benchmark code does not allocate per call to create an input vector. Duplicate
checks include the production API and actual module lease. Unique-module
samples include construction and cleanup, with one cold module before timing.
Output bytes are compared separately, outside timing. All tracked owners are
released after each executable. Seven alternating pairs run with compiler
processes terminal; results below are medians and observed min/max in ms.

recycle their slots/payloads within the module lease. The new keys prevent
that growth before encoding or allocation. This is compilation scratch growth,
not a claim that these particular records caused a VRAM leak.
