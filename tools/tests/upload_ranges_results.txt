Borrowed upload-range filtering, Vulkan and D3D12
================================================

Change and ownership
--------------------
SharedMemory::RequestRange produces GPU-thread scratch and synchronously calls
the backend UploadRanges. Both backends used another vector<pair<uint32,uint32>>
to copy every CPU-upload range after GPU memexport refresh. They now borrow an
exclusive mutable xe_upload_range span from the existing owner and compact it
in place with a C89 helper. Both extra vectors and their high-water allocations
are removed. The common producer fills POD first/second fields directly instead
of assigning temporary std::pairs. The tested record size remains eight bytes.

Before the first removed range, surviving records are already in their final
slots and are not written. After a hole, only survivors move into consumed
source slots. Stable order, fields, count and front/back upload bounds match
the former vector. An all-CPU list is borrowed unchanged; an all-GPU list
returns without metadata movement. A mixed list can still move eight bytes per
survivor after the first hole. This is not universally zero-copy filtering.

The refresh helper is called once for each original input in the same order.
Source review of both EnsureMemexportRangeInDeviceBuffer implementations and
GatherMemexportCopyRuns found GPU copy/barrier recording, with no recursive
SharedMemory::RequestRange call. MakeRangeValid remains at the same points,
including before the actual CPU memcpy; this is required to preserve concurrent
guest invalidation behavior. Imported guest-RAM zero_copy_ early paths, trace
events, native payload uploads, barriers and submission ordering are unchanged.

No native GPU command retains this CPU metadata. The backend cannot retain or
recursively reuse the borrowed source span. RequestRange does not use the old
source records after UploadRanges returns. On later retry it regenerates ranges
from page validity, rather than relying on an unmodified old scratch list.
No locks, clocks, pacing, audio or shutdown behavior changed.

This filtering checkpoint initially retained the source FixedVMemVector scratch
and bitmap scanner. The subsequent C89 scan/atomic-validity migration and its
coverage are recorded in upload_scan_results.txt. Other renderer allocations,
payload copies and required synchronization still remain.

CPU metadata reference/benchmark
-------------------------------
tools/tests/upload_ranges_bench.cc implements the legacy vector<std::pair>
selection and the production C89 compactor. Each regenerates its source list,
filters it, then invokes a noinline checksum consumer so selected fields are
read from actual storage. Matching checksums complement the C leaf's exact
order/content checks. No GPU callback/driver cost is simulated. Allocation
instrumentation covers only the legacy destination vector, since the producer
scratch exists in both implementations. Timings include generation and checksum.

Exactly 33,554,432 (32 Mi) measured source visits per case; 1,000 warm
batches, median of three sequential CPU runs with owned builds finished.
GCC/MinGW g++ -std=c++20 -O2 -Wall -Wextra -Werror; MSVC /O2 /std:c++20 /EHsc.
C++ is only the old-container reference/benchmark; production filtering is C89.

already zero. The common producer scratch is unchanged and excluded on both
sides. These requested payload totals exclude allocator bookkeeping and do not
measure RSS. Near-equal mixed timings should not be read as a robust speed gain.

Reproduce by compiling the benchmark with the flags above, -Ilibretro and
-Ithird_party/libretro-common/include (MSVC /I equivalents). No native GPU,
frontend, shader compiler or game is needed.
