XContent package header VFS (0177)
=================================
Behavior reference: WizzardSK/xenia-libretro commit7708da9f5aee8580355b616b4d3e585ca56acb9a
(Edge-origin failed package-open handle leak). This is an independent C89/VFS
adaptation, not a cherry-pick of its stdio/filesystem implementation.

CreateContentDevice now probes signature + big-endian volume type using one
read-only common VFS handle. Minimum size and field bounds are preflighted;
only eight bytes are requested on a supported package. No full header is
allocated/read simply to select STFS versus SVOD. Invalid magic/type, size,
seek/read errors and close failures cannot publish a type.

Initialize reads directly into the already-owned header, closes that handle
before SetupContainer/LoadHostFiles, then validates the magic and publishes
files_total_size_. It no longer allocates/replaces a second header or leaks
the successful header FILE. The factory's short-file/failed-read FILE leaks are
also removed. The FILE* reader overload is deleted (no external callers).
Standalone ReadContainerHeader(path) uses the same checked VFS transfer into
its final typed allocation. File size comes from the open handle, rather than
a separate path stat; there is no whole-package slurp or payload staging.

On the tested native ABI sizeof(XContentContainerHeader)=38,682 bytes and the
volume type occupies four bytes at offset937 (0x3A9). The factory+Initialize
header sequence requests 38,690 bytes instead of77,364 and uses one header
allocation instead of three. These counts exclude separate signature detection,
metadata extraction and payload mounting elsewhere. A common RFILE wrapper and
UTF-8 path conversion can still allocate; this is not allocation-free mounting.
The constructor retains its original zero-initialized public header state.

The adversarial frontend VFS has no native file behind its UTF-8 content:// URI.
It checks all three signatures, both supported types, a high-byte unsupported
type, exact probe/read byte counts, INT64_MAX logical file size, 1..7 byte reads,
EINTR retry, EOF after a prefix, read errors/oversized returns, size/open/seek
failures and wrong seek results, close errors, no type/size publication on
failure, and exactly one close attempt per successful open. Actual factory and
ReadContainerHeader paths are exercised. A minimal container subclass runs the
real Initialize but replaces payload mounting; it verifies that header failure
never reaches payload hooks and success keeps the original destination address.

No std::filesystem exists/is_directory/file_size or stdio open/read/close remains
in xcontent_container_device.cc. Existing std::filesystem::path-typed public ABI
and UTF-8 conversion are still interoperability boundaries; fragment/payload I/O,
directory traversal, remaining path objects and container-tree synchronization
are separate migration work. No audio/video pacing, sleeps, threads or GPU waits
are added. Remote CI, full Linux core build and live-game mounting have not been
run for this patch; no gameplay/FPS benefit is claimed.

2026-11-07 follow-up: seek status regression
-----------------------------------------
The earlier fake VFS incorrectly returned the new offset for successful seek.
The owned common VFS API and native fallback return zero, so nonzero-offset
volume probes rejected real files. The probe and fake now use status semantics;
unexpected positive status still rejects without publishing a type.

The C89 driver now creates native files for both volume types, probes their
nonzero-offset volume fields, compares direct header bytes and removes the file.
MSVC /TC /W4 /WX driver plus actual C++ XContent factory passes with the current
container owner explicitly compiled and linked ahead of the existing libraries.
Linux C89 ASan+UBSan passes. Compiling the identical driver against the previous
header and selecting native-only execution fails at the volume probe (exit 1),
without invoking the fake VFS. Existing adversarial short-transfer/EINTR/failure
and exact-once-close cases pass. Full exact-commit core builds and live mounting
were not rerun for this one-line correction. Larger SVOD migration remains WIP.
