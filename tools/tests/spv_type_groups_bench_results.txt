Parent: complete 3a5d2b18155b62e6741362d297a840933c65b022 sources.
Windows x64 GCC 16.2 -O2; native MSVC and WSL ASan/UBSan separately checked.

Both groupedTypes and groupedDebugTypes maps of vectors are removed. An exclusive
C89 registry retains per-key contiguous pointer arrays across compiler module
leases. The registry is metadata only: all existing type equality predicates,
layout exclusions, deliberately distinct structs, debug lookups and forward
pointer patching remain unchanged. It does not hash mutable type payloads or
reinterpret identical operands as identical decorated types. The existing
explicitlyLaidOut set remains. Keys separate core and nonsemantic opcodes.

Twenty-four indexed searches, two debug range walks and six singleton lookups
now borrow group views once, rather than repeatedly probing a map. The pointer
type feature pass in post-processing uses the same borrowed view. Array elements
are void* values converted individually at the typed boundary; there is no
Instruction**/void** type-punning. Instruction addresses and operand storage do
not move. Other metadata containers and driver allocations remain.

Group descriptors are a checked open-addressed key registry. Each group owns a
retained C89 pointer buffer; append growth copies only live pointer metadata,
never instruction payloads. Growing the descriptor table does not move another
group's pointer array. A view expires on its own group's mutation or module end.
Epoch reset invalidates old views without dereferencing retired records; wrap
preserves occupied keys and buffers while marking their logical contents stale.
Groups/buffers have no fixed-count restriction. Failed growth keeps prior live
records accessible. Arena close frees every buffer and descriptor allocation
using the same C allocator hooks as growth. Group insertion/publication follows
the previous builder's ordering; no stronger rollback guarantee is claimed for
later unrelated type debug/ID-map failures.

Cold compiler setup reserves 64 descriptors and four pointers for each of 14
common core type opcodes. On measured x64 builds this is 2048 + 448 bytes, plus
32 bytes of registry owner state. Extended/debug groups and larger groups grow
on demand and retain their high-water capacity. There can still be allocations
for new larger workloads; this is not complete runtime-allocation elimination.
GCC x64 Builder 1864 -> 1752 bytes. Instruction64/Block136/Function136/Module88
stay unchanged. The retained-workspace increase below is intentional, not a leak.
